Carta di bawah menerangkan keseluruhan kitaran hayat (lifecycle) sistem dari minit ke minit secara terperinci.

    loop Every 60 Seconds

                TE->>TE: Kira Virtual SL, Virtual TP, Trail Start
                TE->>DB: POST ke `active_trades` (Termasuk be_offset_pips dll)
                TE->>DB: PATCH `signals` (is_active=False)
            end
        end

        note over TE, DB: AI Trade Evaluator (Penjaga Floating)
        TE->>DB: GET `active_trades` (current_status=OPEN)
        TE->>MA: Semak minit (Setiap 5-10 min)
        opt Masa Penilaian
            TE->>MA: Tanya AI (HOLD / CLOSE / UPDATE_SL)
            opt Jika AI suruh CLOSE
                TE->>MT5: mt5.PositionClose(ticket)
            end
        end

        TE->>MT5: Ambil semua posisi terbuka dari Terminal
        TE->>DB: Sync profit semasa / Tembak masuk trade manual jika tiada
    end

    note over EA, DB: MQL5 EA (Penjaga Grid & Safety Net)
    loop OnTimer() Setiap 1 Saat
        EA->>DB: GET /rest/v1/active_trades
        EA->>EA: Lukis garisan Virtual SL, TP, BE/Trail di chart
        EA->>MT5: Semak harga semasa vs garisan Virtual
        opt Harga Langgar Virtual SL / TP
            EA->>MT5: trade.PositionClose()
            EA->>DB: POST ke `closed_trades` & DELETE dari `active_trades`
        end
        opt Floating Minus lebih dari Jarak Grid ATR
            EA->>MT5: Buka Layer Baru (Grid)
            EA->>DB: POST Layer Baru ke `active_trades`
        end
    end

2. Deep Dive: Modul & Tanggungjawab

🤖 bot_manager.py (The Orchestrator)

Tugas: Menguruskan semua proses Python supaya sistem tidak pernah mati.

  • Melancarkan 1 proses master_analyzer.py.
  • Melancarkan 1 proses trade_evaluator.py untuk setiap akaun yang ditanda 'enabled' di Supabase.
  • Supabase Watchdog: Setiap 15 saat, ia query Supabase. Jika anda OFF kan akaun di Web App, ia terus .kill() proses akaun tersebut. Jika anda ON kan, ia .start().
  • Ghost Buster: Semasa start, ia akan bunuh semua "Ghost Python Processes" yang tertinggal dari sesi sebelum ini menggunakan Powershell command.

🧠 master_analyzer.py (The Brain)

Tugas: Pencari setup dan penghasil signal.

  • Berjalan dalam while True (tidur 60 saat).
  • Schedule Checker: Memeriksa minit semasa. Scalping (Setiap 30 min), Intraday (Setiap jam), Swing (Setiap 2 jam).
  • Menghubungi MT5 Master (akaun khas tanpa trading) untuk sedut ribuan data OHLC, Tick, dan Indikator.
  • Menghantar data ke ai_engine.py yang akan panggil API (Groq Llama / DeepSeek).
  • Menulis keputusan akhir ke Supabase signals. AI tidak mempunyai akses MT5 untuk trade!

🛡️ trade_evaluator.py (The Executor)

Tugas: Eksekusi entry, Risk Management, & Evaluate floating trades.

  • Berjalan serentak (Multi-processing) bagi setiap akaun.
  • Risk Guard: Sebelum entry, ia check Spread Point, Max Drawdown, dan blok jika ada High Impact News.
  • Stealth Entry: Menggunakan mt5_connector.py (modul khusus Python-MT5 API) untuk execute order_send() tanpa SL dan TP sebenar bagi mengurangkan pendedahan paras SL/TP kepada broker dan mengekalkan kawalan exit secara internal.
  • Supabase Sync: Merekodkan trade ini ke active_trades bersama kiraan virtual_sl, virtual_tp, dan data BE/Trail dari style_params.py.

🔌 mt5_connector.py & launch_terminals.py (The Adapters)

Tugas: Menjaga komunikasi fizikal dengan perisian MT5.

  • launch_terminals.py: Skrip yang berjalan semasa startup. Ia membaca path `.exe` MT5 dari `.env`, melancarkan perisian tersebut secara automatik, dan melakukan Auto-Login ke dalam akaun (tanpa campur tangan manusia).
  • mt5_connector.py: Modul wrapper khusus. Berbeza dengan supabase_sync.py yang urus pangkalan data awan, modul ini bertindak mengawal arahan terus ke graf MT5 tempatan seperti order_send() (Stealth Entry) dan membaca mt5.positions_get().

☁️ supabase_sync.py (The Nervous System)

Tugas: Jambatan antara kod tempatan (Local) dan Cloud Database.

  • Menggunakan REST API biasa (Requests) berbanding library Supabase yang rasmi bagi mengelakkan isu "Event Loop" di dalam thread Python.
  • Mempunyai fungsi _upsert (Update or Insert) berasaskan Conflict Resolution (seperti on_conflict=ticket).
  • Ini bermakna MT5, Master Analyzer, dan Trade Evaluator tidak pernah berhubung secara "Direct". Mereka semua bersembang melalui Supabase.

⚡ InvestmentAI_Executor.mq5 (The Muscle)

Tugas: Pengawal graf 24/7 di hadapan mata anda.

  • Diletakkan pada chart di MT5 anda. Mempunyai fungsi OnTimer() yang berjalan setiap saat.
  • Menggunakan WebRequest() untuk tarik data active_trades dari Supabase.
  • Grid Master: Menjaga jarak Layer (Averaging). Jika margin merah cecah ATR, ia lepaskan peluru kedua.
  • Menjalankan Break-Even (BE) dan Trailing Stop Virtual, bermaksud garisan ditarik di skrin tetapi tidak dihantar ke broker. Jika langgar, MT5 akan execute close segera!

3. Anatomi Database (Supabase Schema)

Bagaimana maklumat diikat bersama.

  • account_settings: Menyimpan API Keys, Drawdown limit, % target harian, status bot (Enabled/Disabled). Diperiksa oleh Bot Manager.
  • system_settings: Menyimpan senarai pair (XAUUSD, EURUSD), senarai AI Model (Groq, DeepSeek). Diperiksa oleh Master Analyzer.
  • market_signals: Arkib signal mentah dari AI. (Log sejarah AI).
  • signals: Peti surat peribadi bagi setiap akaun. Mengandungi is_active=True/False. Trade Evaluator sentiasa periksa table ini.
  • active_trades: Jadual paling kritikal. Menyimpan status live (OPEN). Dibaca oleh MQL5 EA untuk melukis garisan dan execute Layer/Grid/Trailing.
    *Nota Kritikal: Jadual ini WAJIB mempunyai column be_offset_pips, trail_start_pips, dll, jika tidak Python akan gagal memasukkan data SL/TP!

🚨 Kenapa Sistem Gagal Menulis Virtual SL (Isu '-' di Dashboard)?

Berdasarkan log yang dikesan semasa runtime:
Supabase sync failed 400: {"code":"PGRST204","message":"Could not find the 'be_offset_pips' column of 'active_trades' in the schema cache"}

Ini bermaksud proses Trade Evaluator (Python) BERJAYA mengeksekusi entry di MT5, kemudian ia menghasilkan JSON Payload yang mengandungi data virtual_sl dan virtual_tp untuk dihantar ke Supabase. Namun, Supabase Server Menolak (Reject) payload tersebut kerana jadual (table) active_trades di cloud tidak dikemaskini dengan kolum-kolum baru bagi V4. Oleh sebab payload ditolak, data SL dan TP anda terpadam di udara dan Dashboard membaca nilai kosong -.

5. Edge Cases & Advanced Configurations

Di bawah ini merangkumi mekanik terperinci untuk pengurusan risiko, pelan sandaran (failover), dan formula logik konkrit.

🧮 Lot Size & Risk Calculation

Lokasi: account_settings.py

  • Sistem tidak menggunakan Fixed Lot buta-buta.
  • Ia mengira: Lot = (Balance * Risk_Percentage) / StopLoss_Pips / Pip_Value.
  • Nota Penting: Pip value mesti dikira secara dinamik berdasarkan symbol_info.trade_tick_value, trade_tick_size, contract size, dan mata wang akaun broker bagi mengelakkan kesalahan pengiraan lot untuk pair XAUUSD.
  • Jika baki naik (compound), lot size akan automatik membesar secara berperingkat berdasarkan Risk Per Trade yang diset (Contoh: 2%).

📏 Parameter Trailing (style_params.py)

Isu: Punca utama kegagalan menulis SL (Error `-`).

  • Fail ini membekalkan titik Breakeven dan Trailing Stop sebenar untuk XAUUSD.
  • SCALPING: be_offset_pips = 2 pips, trail_start_pips = 20 pips.
  • INTRADAY: be_offset_pips = 5 pips, trail_start_pips = 60 pips.
  • SWING: be_offset_pips = 10 pips, trail_start_pips = 120 pips.
  • Data konkrit ini disuntik ke dalam Supabase untuk dibaca oleh MQL5. Tanpa parameter ini, EA gagal melakukan Trailing.

🗞️ High-Impact News Filter

Lokasi: news_manager.py

  • Sumber: Mengambil fail XML / JSON dari ForexFactory.
  • Logic Blok: Jika terdapat berita "High Impact" (merah) untuk pair USD, sistem akan menyekat sebarang entry baru 30 minit sebelum dan 30 minit selepas berita dikeluarkan.
  • Ini mengelakkan AI terperangkap dalam "slippage" atau "spread hantu" ketika news rilis.

🌐 AI Failover & Rotation

Lokasi: ai_clients / ai_engine.py

  • Sistem menyokong provider pelbagai seperti Groq dan DeepSeek.
  • Jika Groq API terputus (Timeout/Rate Limit), sistem mempunyai fungsi Exponential Backoff Retries (cubaan berulang dengan masa tertunda 2s, 4s, 8s).
  • Jika masih gagal selepas had percubaan, modul boleh jatuh sandaran (fallback) kepada model / provider kedua bagi memastikan aliran signal tidak terputus.

👁️ Trigger Vision Engine [EXPERIMENTAL]

Lokasi: vision_engine.py

  • Vision AI tidak dipanggil untuk setiap kali semakan (kerana kos token imej tinggi).
  • Ia bertindak sebagai Tie-Breaker. Jika text-analyzer memberikan keyakinan (confidence) yang sangat rendah atau pasaran sangat Ranging, Vision API akan diaktifkan untuk melihat "Price Action" dan Pola Candlestick.

🕸️ MQL5 Grid Logic Formula

Lokasi: InvestmentAI_Executor.mq5

  • Penanda Jarak: EA tidak tembak layer setiap 10 pip. Ia menggunakan Indikator ATR pada timeframe semasa untuk menentukan "volatility".
  • Trigger: Jika margin negatif melebihi nilai `ATR * Multiplier`, EA akan lepaskan Layer 2.
  • Max Layers: Tetapan sistem mengehadkan MAX_TRADES_PER_PAIR = 10 layer sahaja bagi setiap instrumen untuk mengelakkan Margin Call mutlak.
  • Pengurusan SL/TP Layer Baru: Apabila layer baru dibuka, EA akan recalculate harga purata (Average Entry Price). Virtual TP dan SL akan dianjak secara automatik untuk menyesuaikan dengan harga purata yang baru (Basket Take Profit).

⚔️ Race Condition (Konflik Penutupan)

Isu: Bagaimana jika Python (AI Close) dan MQL5 (Sentuh Virtual SL) cuba menutup trade yang sama pada saat yang sama?

  • Ini dipanggil konflik eksekusi serentak.
  • Penyelesaian: Python akan set closing_requested = true, menghantar arahan close ke MT5, kemudian verify semula melalui mt5.positions_get(). Jika close gagal, status dikembalikan kepada OPEN atau dimasukkan ke dalam retry queue.
  • MQL5 sentiasa memeriksa kewujudan tiket di memori lokal/Supabase sebelum menembak arahan PositionClose(). Jika Python sedang memproses penutupan, MQL5 mengabaikan posisi tersebut bagi mengelakkan error "Invalid Ticket".

🔄 Recovery Protocol (Python Crash)

Kes: Python mati selepas open trade.

  • MQL5 EA ada Safety Net dan akan terus menjaga trade yang terbuka di MT5.
  • Apabila bot_manager menghidupkan semula Python, Python akan query mt5.positions_get(), melihat ada trade aktif, dan Sync Semula (Re-attach) maklumat P/L ke dalam Supabase untuk menyambung tugas Trade Evaluator seolah-olah tiada apa yang berlaku.

6. Keselamatan & Data Skema Tambahan

🔒 Supabase RLS & Kunci Akses (Security)

Oleh kerana sistem berkomunikasi secara Cloud-Native menerusi REST API Supabase, struktur keselamatan berbilang lapisan diperlukan.

Frontend Dashboard: Hanya dibenarkan menggunakan anon key dengan perlindungan RLS (auth.uid() = user_id).

Backend Python: Boleh menggunakan service_role key (disimpan selamat dalam VPS `.env`) untuk bypass RLS ketika memproses signal secara pukal.

MQL5 EA: Tidak dinasihatkan menyimpan `service_role` terus di dalam kod EA; komunikasi EA wajar dihadkan melalui Anon Key berserta penapis account_id, atau melalui Supabase Edge Functions / Proxy selamat.

🗄️ Table `closed_trades`

Apabila MQL5 atau Python selesai menutup trade, data tersebut dipadam dari active_trades dan dilempar ke closed_trades.

Kolum Utama: ticket, symbol, pnl, closed_at, close_reason (Hit TP, Hit SL, AI Close).

Ini membolehkan Dashboard Web anda menjana carta prestasi harian (Win Rate) secara real-time.

7. Skema Pangkalan Data Induk (SQL DDL)

Ini adalah jadual paling kritikal (active_trades) yang menghubungkan MQL5 dan Python. Wajib dipastikan sama bentuk di Supabase.

-- active_trades (struktur skema mandatori)
CREATE TABLE active_trades (
  id bigint generated always as identity primary key,
  ticket bigint not null unique,
  account_id text not null,
  symbol text not null,
  direction text not null,  -- BUY / SELL
  lot double precision not null,
  trade_style text,         -- SCALPING / INTRADAY / SWING
  virtual_sl double precision,
  virtual_tp double precision,
  be_offset_pips double precision,   -- Pencetus Breakeven
  trail_start_pips double precision, -- Jarak Trailing
  trail_dist_pips double precision,
  entry_price double precision,
  average_entry_price double precision,
  layer_index int default 1,
  basket_id text,
  magic_number bigint,
  current_profit double precision,
  closing_requested boolean default false,
  close_requested_by text,
  close_requested_at timestamptz,
  updated_at timestamptz default now(),
  opened_at timestamptz default now(),
  current_status text default 'OPEN',
  signal_id text, -- ID Isyarat Asal
  CONSTRAINT unique_account_signal UNIQUE (account_id, signal_id) -- Halang Duplicate Entry
);
-- closed_trades (struktur arkib sejarah)
CREATE TABLE closed_trades (
  id bigint generated always as identity primary key,
  ticket bigint not null unique,
  account_id text not null,
  symbol text not null,
  direction text not null,
  lot double precision,
  trade_style text,
  pnl double precision,
  close_reason text,  -- Hit TP, Hit SL, AI Close
  closed_at timestamptz default now()
);

8. Kontrak API (Komunikasi Cloud-Native)

Sistem ini tidak menggunakan fail TXT/CSV. Semuanya berkomunikasi merentasi benua (Server ke MT5) melalui REST API Supabase.

Penghantar Kaedah Endpoint Tujuan
Master Analyzer POST /rest/v1/signals Menghantar surat arahan entry dari AI ke semua akaun.
Trade Evaluator GET /rest/v1/signals?is_active=eq.true&account_id=eq.XXX Membaca jika ada arahan entry baru dari otak utama (Isyarat bersifat Per-Akaun).
Trade Evaluator POST / PATCH /rest/v1/active_trades Lepas entry di MT5, simpan rekod Virtual SL/TP.
MQL5 EA GET /rest/v1/active_trades?account_id=eq.XXX&current_status=eq.OPEN Tarik data Virtual SL/TP setiap 1 saat untuk lukis garisan chart secara spesifik (elak Rate Limit).

Contoh JSON Payload & Pengendalian HTTP 409

Apabila `trade_evaluator.py` menembak rekod baru ke jadual active_trades, ia akan menghantar payload JSON seperti berikut:

{
  "ticket": 1234567,
  "account_id": "ACC-001",
  "symbol": "XAUUSD",
  "direction": "BUY",
  "lot": 0.05,
  "trade_style": "SCALPING",
  "virtual_sl": 2315.50,
  "virtual_tp": 2320.00,
  "signal_id": "SIG-998877"
}

Nota Isyarat Pendua (Duplicate): Disebabkan wujudnya constraint unique_account_signal dalam DDL, jika Python cuba memasukkan isyarat (`signal_id`) yang sama buat kali kedua, Supabase secara automatik akan memulangkan ralat HTTP 409 (Conflict). supabase_sync.py wajib mengendalikan ralat 409 ini dengan lancar—iaitu dengan merekodkan log amaran ("Trade already exists") tanpa menyebabkan bot terhenti (crash).

9. Skop Kerja: Python vs MQL5

Ini perbezaan ketara tanggungjawab antara kedua-dua modul pelaksana ini untuk elak kekeliruan pemaju.

🐍 Python (Trade Evaluator)

  • Buka Trade Pertama (Stealth Entry).
  • Tulis data SL/TP Maya ke Supabase.
  • Tanya AI adakah patut HOLD atau CLOSE trade yang sedang berjalan (setiap 5 minit).
  • TIDAK melukis apa-apa di skrin MT5.
  • TIDAK menguruskan Layer / Grid.

⚡ MQL5 (Expert Advisor)

  • Baca data Supabase dan lukis garisan Virtual SL/TP/Trail di MT5.
  • Menutup trade (Close) sepantas kilat jika harga kena garisan maya.
  • Buka layer averaging (Grid) jika market junam melepasi Jarak ATR.
  • TIDAK berinteraksi langsung dengan AI.
  • TIDAK buat entry pertama.

  • Semak fail logs/bot.log atau logs/master_analyzer.log jika sistem kelihatan terhenti.

11. Production Readiness & Safety Checklist

Sebelum menjalankan sistem pelaburan AI ini ke akaun Live dengan saiz dana yang besar, pastikan 7 lapisan "Fail-Safe" dan prosedur ini dipatuhi sepenuhnya.

🚨 1. Emergency Safety Layer (Hard SL)

Isu: Bergantung 100% pada Virtual SL sangat berbahaya jika VPS/Internet terputus atau MT5 freeze.

  • Solusi: Walaupun menggunakan Virtual SL/TP untuk elak tatapan Broker, setiap entry dari Python WAJIB diselitkan dengan Hard Emergency SL. Emergency Hard SL patut dikira secara dinamik menggunakan ATR multiplier atau equity-risk cap, contohnya Emergency_SL = max(Virtual_SL_Distance * 3, ATR * 5).
  • Ini adalah perlindungan mutlak jika kesemua sistem (MQL5 + Python + Supabase) gagal berfungsi serentak.

🛑 2. Kill Switch & Daily Limit

Isu: Robot tidak mempunyai perasaan dan boleh berterusan membuka trade (Grid) walaupun market sedang hancur.

  • Global Kill Switch: Mesti ada butang fizikal atau tetapan pangkalan data untuk menghentikan serta-merta sebarang signal baru.
  • Daily Limits: Hadkan Max Daily Loss, Max Consecutive Losses, dan Max Grid Layers di dalam tetapan supaya MQL5 hanya fokus pada risk reduction selepas limit dicapai.

✅ 3. AI Validation Layer (Sanity Check)

Isu: AI boleh berhalusinasi, memulangkan JSON rosak, atau SL/TP yang melawan logik akal.

  • Sanity Check Python: Python trade_evaluator akan reject (tolak) isyarat jika sl_price / tp_price kosong, atau R:R (Risk-to-Reward) terlalu rendah.
  • Logical Check: Tolak jika trade BUY tetapi SL diletak di atas harga entry. Fallback kepada HOLD/Abaikan jika AI response invalid.

📊 4. Testing & Validation Plan

Isu: "Macam mana nak tahu AI ni betul-betul profitable?"

  • Jalankan Backtest minimum 3-6 bulan untuk melihat cara MQL5 Grid bertahan.
  • Forward test di akaun Demo selama 4 minggu untuk memastikan Latency Supabase & kelajuan MT5.
  • Kumpul data Win Rate, Profit Factor, dan purata R:R secara berasingan untuk Scalping vs Swing.

🔔 5. Heartbeat & Pusat Kawalan (Alert)

Isu: Sistem cloud yang berjalan "senyap" amat berisiko. Bagaimana jika VPS 'hang' tanpa kita sedar?

  • Heartbeat Timestamp: Wujudkan satu column last_seen_bot di Supabase. Python perlu update timestamp ini setiap 60 saat.
  • Jika tiada update melebihi 60 saat, Dashboard Web App akan automatik memaparkan status OFFLINE dan menghantar amaran Telegram kepada anda.
  • Sistem juga mesti menghantar Telegram Alert bagi setiap pertambahan Grid Layer, Error Code 400 (Supabase), atau Provider AI Timeout.
  • Contoh Notifikasi Telegram: [🚨 OFFLINE] Akaun 12345: Tiada heartbeat dari VPS melebihi 60 saat! atau [✅ AI ENTRY] XAUUSD BUY (Lot 0.05) @ 2315.00.

🗃️ 6. Supabase Migration Checklist

Isu: Menghalang Error PGRST204 (Column Not Found) & Isu Duplicate.

  • Laksanakan skrip migrasi SQL (pastikan `signal_id` ujud untuk Duplicate Trade Protection).
  • Refresh Supabase Schema Cache.
  • Uji insert sample payload dari Postman/Thunder Client.
  • Pastikan Polisi RLS dikuatkuasakan dengan sempurna.

🔐 7. Security & API Protection

Isu: Kebocoran wang dan data peribadi.

  • JANGAN hardcode sebarang API key di dalam fail .py. Semua kunci (Groq, DeepSeek, Supabase URL) wajib disimpan dalam fail .env.
  • Jangan sesekali expose kunci Service Role Supabase kepada pihak luar. Gunakan Anon Key sahaja dengan perlindungan RLS.

⏱️ 8. Rate Limit & Polling MQL5

Isu: EA yang menarik (GET) rekod Supabase setiap 1 saat berisiko kena ban kerana melanggar had API Rate Limit.

  • Jika terdapat 10 akaun, ia bermakna berpuluh ribu request sehari yang akan memberatkan server Supabase percuma.
  • Solusi: EA harus hanya mengambil data yang statusnya OPEN dan ditapis menggunakan param account_id=eq.XXX. EA juga boleh digabungkan dengan teknik pemprosesan timestamp cache (hanya GET bila timestamp terkini berbeza).

12. Web App Dashboard (Kawalan Jauh)

📱 frontend-dashboard (Next.js & Supabase)

Fungsi: Antaramuka kawalan peribadi yang membolehkan anda memantau bot dari telefon pintar (tanpa perlu Remote Desktop ke VPS).

  • Toggle ON/OFF: Update status `enabled=true/false` di jadual `account_settings`. `bot_manager` di VPS akan automatik menghidupkan/mematikan akaun tersebut dalam 15 saat.
  • Live Status: Membaca timestamp `last_seen_bot` untuk memaparkan Heartbeat ONLINE / OFFLINE / WARNING secara real-time.
  • Telegram Alert: Walaupun Web App boleh memaparkan log graf, Telegram/WhatsApp Alert tetap berjalan selari di latar belakang (diurus oleh Python) untuk push notification pantas bila wujud isyarat kritikal.
  • Hosting: Boleh di-host pada Vercel secara percuma. Berkomunikasi terus ke Supabase dengan RLS (hanya pengguna Auth yang sah boleh akses).
